# 0007. PyMuPDF の呼び出しをグローバルロックで直列化する

- Status: Accepted

## Context

PyMuPDF はスレッドセーフではない。一方、Flask の開発サーバーはリクエストをスレッドで並行処理し、
UI はページ表示のたびに「ページ解析」「キーワード矩形の検索」「ページ画像のレンダリング」を
並行で投げる。同じ `Document` オブジェクトへ複数スレッドが同時に触る構造になっていた。

実際に、並行アクセス時にだけテキスト行の座標が数 pt ずれて返る事象が観測された。
座標はルールの照合キーに保存されるため、化けた座標が永続化されると
以後そのルールがどこにも当たらなくなる。

## Decision Drivers

- 座標・テキストの取得結果が常に正しいこと（照合キーとして永続化されるため）
- 実装の単純さ（利用者は同時 1 人のローカルツール）
- バックグラウンドのキャッシュ温めと通常リクエストの共存

## Considered Options

1. **グローバルな再入可能ロック（RLock）で PyMuPDF を触る区間をすべて直列化する**
2. リクエストごとに Document を開き直す — 開くだけで数百 ms かかり体感が大きく劣化。
   さらに MuPDF はグローバル状態（フォントキャッシュ等）を持つため、
   Document を分けても完全には安全にならない
3. PDF 処理を専用ワーカープロセスに分離する — 最も堅牢だが、シリアライズ層が増え
   この規模のツールには過剰

## Decision

オプション 1 を採用する。`Document` の取得・解析・レンダリング・検索など
PyMuPDF に触るすべての区間を単一の `threading.RLock` で囲む。
長時間走るバックグラウンド処理（キャッシュ温め）は 1 ページごとにロックを取り直し、
通常リクエストを飢えさせないようにする。

## Consequences

- (+) 並行アクセス起因の座標化けが構造的に起きなくなる
- (+) 再入可能ロックなので、ヘルパー関数の入れ子呼び出しでも安全
- (−) PDF 処理が直列化される（同時 1 人のローカル利用では体感影響なし）
- (−) ロックを取り忘れた新しいコードパスが混入しうる（レビュー観点として明文化）
