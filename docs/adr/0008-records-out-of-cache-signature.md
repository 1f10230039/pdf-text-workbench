# 0008. 人の判断の「記録」はキャッシュ署名に含めない

- Status: Accepted

## Context

解析キャッシュ（L1 の全行）は「PDF の更新時刻 ＋ 設定の署名」で有効性を判定している
（→ [ADR-0002](0002-settings-json.md)）。設定 JSON には 2 種類の内容が同居している：

1. **抽出を変えるもの** — 境界の余白、除外ページ、結合・分割のルールなど
2. **判断の記録** — 「境界を点検して問題なしと結論した」「この単位を目視確認した」という、
   出力には影響しない監査用のメタデータ

当初の署名は設定 JSON のほぼ全体から作られており、記録フィールド（`boundary_check` /
`task_states`）も含まれていた。その結果、**「問題なし」と記録しただけで全文解析の
キャッシュが無効になり、全文書が「要再解析」表示になる**事象が実際に起きた。
数十文書 × 数十秒の再解析が、出力の変わらない操作のたびに発生することになる。

## Decision Drivers

- 記録する行為が再解析を誘発しない（点検・確認のテンポを壊さない）
- 署名は「同じ署名なら同じ出力」を保証し続ける（キャッシュの正しさ）
- 判定は 1 か所（`cachekit.py`）で管理し、UI とバッチで食い違わない

## Considered Options

1. **署名から記録フィールドを除外する**（除外リストを `cachekit.py` に一元管理）
2. 記録を設定 JSON と別ファイルに分ける — 「1 文書 1 ファイルに判断がすべて残る」という
   監査上の利点（ADR-0002）を失い、ファイルの対応関係の管理が増える
3. 記録時だけキャッシュ無効化をスキップする特例処理 — 呼び出し側の実装依存になり、
   バッチや将来のコードが同じ特例を踏み外す

## Decision

オプション 1 を採用する。抽出結果を変えないフィールド
（`unit_merges` / `unit_excludes` / `unit_checks` / `boundary_check` / `task_states`）を
署名の計算から除外する。除外リストは `cachekit.py` に置き、判定ロジックを 1 か所に保つ。

記録に対応する**実際の変更**（例：点検の結果として境界の余白を変えた）は、
変更されたパラメータ自身が署名を変えるので、必要な再解析は今までどおり起きる。

## Consequences

- (+) 点検・確認・結論の記録が、再解析を一切誘発しなくなる
- (+) 「抽出を変えるもの／記録」の区別が除外リストとして明文化される
- (-) 新しい記録フィールドを追加するときは、除外リストに入れるかを毎回判断する必要がある
  （入れ忘れると同種の全文書再解析が再発する）
- 署名の形が変わるため、導入時に既存キャッシュは 1 回だけ全文書で作り直しになる
