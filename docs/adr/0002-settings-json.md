# 0002. すべての手動操作を設定 JSON に記録して再現性を担保する

- Status: Accepted

## Context

PDF のレイアウトは文書ごとに違い、機械判定だけでは必ず取り切れない箇所が残る。
一方で、その場しのぎの手修正は「なぜその出力になったのか」を説明できなくし、
同じ入力から同じ出力を再現できなくする。コンテンツ分析の前処理として使う以上、
**第三者が同じ結果を再現できること**は譲れない要件になる。

## Decision Drivers

- 同じ PDF から常に同じ出力が得られること（決定性）
- 手を入れた箇所を全件列挙できること（監査可能性）
- 「なぜそうしたか」を後から説明できること
- 修正のたびに確認ダイアログを挟まない操作感（作業は数百件規模になる）

## Considered Options

1. **手動操作をルールとして文書ごとの JSON に記録し、抽出時に毎回適用する**
2. 抽出結果（テキスト）を直接編集する — 再現性がなく、元 PDF 更新で全修正が消える
3. 修正をアプリ内 DB に持つ — 成果物と一緒に持ち運べず、差分レビューもしにくい

## Decision

オプション 1 を採用する。除外・結合・分割・表の指定・種別の上書きなど、
人が加えるすべての操作を**理由コードつきのルール**として設定 JSON に保存し、
抽出のたびに機械判定へ再適用する。

ルールの照合はテキストの完全一致（＋ページ・座標）で行い、
**当たらなくなったルールは黙って捨てずに UI へ警告として出す**。
パラメータ変更でブロックの切れ方が変わったとき、効いていない修正が
残ったまま気づかず先へ進むことを防ぐため。

## Consequences

- (+) 「PDF ＋ JSON → 同じ出力」が成立し、JSON を付ければ第三者が再現できる
- (+) 手動操作の件数と理由の内訳をそのまま報告できる（恣意的な前処理でないことの根拠）
- (+) JSON は差分レビューやバージョン管理に載せられる
- (−) ルールの照合キー設計（同じ文言が複数あるケース等）に継続的な注意が要る
- (−) 理由コードの付与は人の負担になる → 必須にはせず、未設定を UI で可視化するに留める
