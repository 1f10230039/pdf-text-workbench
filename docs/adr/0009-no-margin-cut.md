# 0009. 座標によるヘッダー/フッターの切り取りとページ除外を廃止する

- Status: Accepted

## Context

破壊的な前処理として、当初は 3 つの仕組みを持っていた：

1. **座標カット** — `header_y` / `footer_margin` より外側の行をヘッダー/フッターとして捨てる
2. **ページ除外** — 表紙・目次などを `skip_pages` でページごと捨てる
3. **柱の除去** — 全ページの一定割合以上で「同じ位置に同じ文言」の行を捨てる（`repeat_ratio`）

1 と 2 は文書ごとに値・対象を決める必要があり、そのための確認画面
（機械診断 → 境界値の自動提案 → 人が原本を見て記録）まで作り込んだ。
しかし実文書には**ページ番号と同じ高さに本文が回り込むレイアウト**があり、
座標では機械的に分けられず、結局 1 冊ずつ人の判断が必要になる。
数十冊 × 毎年の運用ではこの判断コスト自体がボトルネックになる。

実測（61 文書）では、座標カットを廃止して新たに入ってくる 15,901 行のうち、
**分析対象キーワードを含む行は 0 件**だった。ナビゲーションの類はほぼ全ページで
反復するため 3 の柱除去が落とし、反復しない残り（ページ番号・章名など）は
分母のノイズにしかならない（全文書一律・機械的）。

## Decision Drivers

- 文書ごとの人の判断をゼロにする（再現性の議論を最強にする：前処理は機械的規則 1 つ）
- 「切りすぎ」は不可逆、「残しすぎ」は後から除外できる — 誤りの被害が非対称
- 分析はキーワードを含む箇所（L2）で行うため、全文（L1）は分母として一律であればよい

## Considered Options

1. **座標カットとページ除外を廃止し、柱除去だけ残す**
2. 文書ごとに境界を確認し続ける（自動提案つき） — 判断コストが残り、
   境界で分けられないレイアウトでは原理的に決められない
3. 既定の境界値を全文書に一括適用 — 本文の巻き込み（不可逆な欠損）が実際に発生した

## Decision

オプション 1 を採用する。破壊的な前処理は**柱の除去 1 つ**（全文書共通・機械的）。
ヘッダー/フッター・表紙・目次に由来する行がキーワードにヒットした場合は、
確認モードで理由コード（ヘッダー / フッター / 目次 / 表紙 など）を付けて
**単位側から**除外する（`unit_excludes`）。除外は監査記録に全件残る。

`header_y` / `footer_margin` / `skip_pages` は設定スキーマから引退し、
古い設定 JSON に残っていても読み込み時に無視される。

## Consequences

- (+) 文書を追加しても前処理の調整・確認作業が発生しない（ゼロコンフィグ）
- (+) 「前処理は反復行の除去のみ。文書ごとのパラメータ調整は行わない」と一文で説明できる
- (+) 切りすぎによる不可逆な本文欠損が構造的に起きなくなる
- (-) 全文（L1）の総行数にページ番号・章名などのノイズが数％入る（全文書一律・機械的）
- (-) キーワードがナビゲーションに載る文書では、確認モードでの理由付き除外が数件増える
- 境界確認の画面・診断 API・関連キャッシュは削除した（実装は履歴に残る）
